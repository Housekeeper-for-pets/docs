## 핵심 설계 결정 요약

| 항목 | 결정 | 이유 |
|------|------|------|
| 구조 방식 | 도메인형 최상위 + 계층형 내부 | 도메인 간 결합도 최소화, 팀원별 도메인 독립 개발 |
| 분산락 공통 모듈 | `global/lock` | 선경안(매칭)·이지민(렌탈)이 동일 Redisson 락 로직 공유 |
| AI 기능 격리 | `global/ai` + 도메인별 AI 서비스 | AI 장애 격리 원칙 (ADR-008) — 핵심 서비스와 분리 |
| Kafka 이벤트 | `global/kafka` Producer/Consumer | 매칭 확정 이벤트를 여러 도메인이 공유 |
| SSE 공통 관리 | `global/sse` | 알림 발송 로직을 단일 모듈로 통합 |
| QueryDSL Custom 분리 | `*RepositoryCustom` | 동적 검색 쿼리를 JPA Repository와 분리 (ADR-007) |
| 에러 단일 정의 | `global/exception/ErrorCode` | 모든 에러를 enum 한 곳에서 관리 |

## 3. `domain` 패키지 상세

### 3-1. `auth` — 인증 (권지원)

```
domain/auth/
├── controller/
│   └── AuthController.java         # POST /api/auth/signup
│                                   # POST /api/auth/login
├── dto/
│   ├── request/
│   │   ├── SignupRequestDto.java    # { email, password, nickname, role } + @Valid
│   │   └── LoginRequestDto.java    # { email, password }
│   └── response/
│       ├── SignupResponseDto.java   # { userId, email, role, createdAt }
│       └── LoginResponseDto.java   # { accessToken, expiresIn, tokenType }
└── service/
    └── AuthService.java            # 회원가입(BCrypt 암호화, 역할별 프로필 초기화)
                                    # 로그인(JWT 발급) — payload: userId, role
```

> **JWT 정책 (ADR-001):** AccessToken 단독 (1시간), Refresh Token v1 미구현.
> 역할(role)은 JWT payload에 포함 → `@PreAuthorize("hasRole('GUARDIAN')")` 접근 제어.

## 5. 주요 Bean 의존 관계

```
[요청 처리 흐름 — 시터 제안 입찰]

POST /api/postings/{postingId}/proposals
  └─▶ SitterProposalController
        └─▶ SitterProposalService
              ├─▶ Redisson tryLock("lock:proposal:{postingId}", wait=3s, lease=10s)
              │     └─▶ 실패 → 429 TooManyRequestsException(PROPOSAL_LOCK_FAILED)
              ├─▶ CarePostingRepository.findById() → OPEN 상태 확인
              ├─▶ SitterProposalRepository.existsBySitterIdAndPostingId() → 중복 체크
              ├─▶ SitterProposalRepository.save() → DB 저장
              ├─▶ carePosting.incrementProposalCount() → Dirty Checking
              ├─▶ Redisson unlock() → finally 블록
              └─▶ SseEmitterManager.send(guardianId, PROPOSAL_ARRIVED) → SSE 푸시


[요청 처리 흐름 — 매칭 확정]

POST /api/postings/{postingId}/proposals/{proposalId}/accept
  └─▶ MatchingController
        └─▶ MatchingService
              ├─▶ SitterProposalRepository.findById() → PENDING 확인
              ├─▶ @Transactional:
              │     ├─▶ Matching INSERT (posting_id UNIQUE → 중복 시 즉시 에러)
              │     ├─▶ CarePosting.status = MATCHED
              │     └─▶ 나머지 SitterProposal.status = REJECTED
              ├─▶ MatchingEventProducer.send("matching-confirmed", event) → Kafka 발행
              └─▶ Response: 200 OK { matchingId, finalPrice }

  병렬 소비자 (Kafka):
    ├─▶ PaymentConsumer     → 결제 처리
    ├─▶ NotificationConsumer → 시터에게 SSE (MATCHING_CONFIRMED)
    └─▶ ScheduleConsumer    → 케어 일정 생성


[요청 처리 흐름 — 렌탈 신청]

POST /api/rentals
  └─▶ RentalController
        └─▶ RentalService
              ├─▶ Redisson tryLock("lock:rental:{itemId}", wait=5s, lease=15s)
              │     └─▶ 실패 3회 → 429 RENTAL_LOCK_FAILED
              ├─▶ RentalItemRepository.findById() → stock 확인
```
