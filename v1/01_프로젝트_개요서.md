## 2. 프로젝트 배경 및 목적

### 배경

국내 반려동물 양육 인구는 약 **1,500만 명**에 달하며 매년 증가하고 있다.
기존 펫시터·케어 서비스(케어네이처, 펫시팅닷컴 등)는 모두 **시터 주도** 구조로, 보호자가 수십 개의 시터 프로필을 일일이 탐색해야 하는 불편함이 있다.
또한 펫시터 예약·용품 렌탈·임시보호 매칭이 각각 다른 플랫폼에 흩어져 있어 통합적인 케어 서비스가 부재하다.

### 목적

- **역방향 매칭 구조** 도입: 보호자가 조건을 공고로 올리면 시터가 역으로 제안하는 구조로, 기존 서비스와의 명확한 차별화
- **동시성 제어 경험**: 동시 제안 입찰, 렌탈 재고 동시 차감 등 실제 트래픽 환경의 동시성 문제 직접 해결
- **AI 기능 통합 경험**: LLM 구조화 출력, Tool Calling, RAG, 장애 격리 등 AI Engineering 역량 습득
- **실배포 경험**: 실제 사용 가능한 수준의 서비스를 AWS 환경에 배포하고 운영

## 3. 서비스 개요

**ForPets(포펫츠)**는 반려동물 보호자가 케어 조건을 공고로 먼저 등록하면, 시터가 역으로 제안을 입찰하는 **역방향 반려동물 케어 매칭 플랫폼**이다.

### 핵심 가치 제안

| 가치 | 설명 |
|------|------|
| 역방향 매칭 | 보호자가 조건 공고 → 시터 역방향 제안 입찰 → 보호자 선택. 기존 어떤 서비스에도 없는 구조 |
| 통합 케어 | 펫시터 매칭 + 용품 단기 렌탈 + 임시보호 매칭을 한 플랫폼에서 해결 |
| AI 시맨틱 매칭 | "분리불안 있는 노령견 경험 있는 시터" 등 자연어로 시터를 탐색하는 RAG 기반 검색 |
| 실시간 케어 | 케어 일지·사진을 SSE로 보호자에게 실시간 푸시 |

## 4. 핵심 비즈니스 로직: 역방향 펫시터 매칭 플로우 ⭐

> 기존 서비스의 시터 주도 구조를 뒤집는 것이 ForPets의 핵심 차별화 포인트다.
> 보호자가 먼저 수요를 공고로 올리고, 시터들이 경쟁적으로 제안을 입찰한다.

### 4-1. 문제 정의

기존 펫시터 플랫폼의 구조:

- **기존 구조:** 시터가 프로필 등록 → 보호자가 수십 개 프로필 탐색 → 예약 요청 → 시터 수락 대기
- **문제점:** 보호자가 탐색·비교에 과도한 시간 소모. 내 반려동물 특성에 맞는 시터를 찾기 어려움. 가격 협상 구조가 없음.

ForPets의 역방향 구조:

- **역방향 구조:** 보호자가 조건 공고 등록 → 시터들이 역으로 제안 입찰 → 보호자가 제안 비교 후 선택
- **효과:** 보호자 탐색 시간 제거. 시터 간 가격 경쟁으로 보호자에게 유리한 조건 형성.

### 4-2. 매칭 상태 머신

```
[OPEN] ──제안 수락──▶ [MATCHED] ──케어 완료──▶ [DONE]
  │                                               │
만료/취소                                       후기 작성
  │                                               │
  ▼                                               ▼
[CLOSED]                                       [REVIEWED]
```

| 상태 | 설명 |
|------|------|
| `OPEN` | 공고 등록 완료, 시터 제안 수락 가능 |
| `MATCHED` | 보호자가 특정 시터의 제안 수락. 케어 진행 중 |
| `DONE` | 케어 완료 확인 |
| `CLOSED` | 기간 만료 또는 보호자 취소 |

### 4-3. 전체 매칭 플로우 (Happy Path)

```
1. 보호자 → 케어 공고 등록 (날짜, 견종, 예산, 요구사항)
2. 시스템 → 조건 맞는 시터에게 SSE 알림 발송
3. 시터들 → 제안 입찰 (proposed_price, message)
   └ Redisson 분산 락으로 동시 입찰 정합성 보장
4. 보호자 → 제안 목록 비교 후 최적 시터 선택
5. 시스템 → Kafka 매칭 확정 이벤트 발행
   └ 결제 처리 + 양쪽 알림 + 일정 생성 비동기 병렬 처리
6. 시터 → 케어 진행 + 일지/사진 업로드
7. 시스템 → SSE로 보호자에게 실시간 케어 일지 푸시
8. 보호자 → 케어 완료 확인
9. 보호자 → 후기 작성 (AI 요약 자동 생성)
```

### 4-4. 동시성 제어 전략

ForPets는 **시터 제안 동시 입찰**과 **렌탈 재고 동시 차감** 두 가지를 주요 동시성 제어 대상으로 설계한다.

```
① 시터 제안 입찰 락   (Redis: Redisson — postingId 기반)
② 렌탈 재고 차감 락   (Redis: Redisson — itemId 기반)
③ DB 트랜잭션         (MySQL: InnoDB)
```

| 시나리오 | 락 키 | 실패 전략 |
|----------|-------|-----------|
| 시터 제안 입찰 | `lock:proposal:{postingId}` | Fail Fast (즉시 실패 반환) |
| 렌탈 재고 차감 | `lock:rental:{itemId}` | Retry with backoff (최대 3회) |
| 매칭 중복 확정 방지 | DB Unique (posting_id) | DB 제약 + 멱등성 키 |

## 7. 동시성 제어 전략

### 7-1. 구현 대상

ForPets는 **시터 제안 입찰**과 **렌탈 재고 차감** 두 가지를 핵심 동시성 제어 대상으로 설계한다.

| 시나리오 | 발생 상황 | 전략 |
|----------|-----------|------|
| 시터 제안 입찰 | 하나의 공고에 여러 시터가 동시 제안 시 `proposal_count` 정합성 | Redisson 분산 락 (postingId 기반) |
| 렌탈 재고 차감 | 마지막 1개 남은 용품에 여러 명이 동시 신청 | Redisson 분산 락 (itemId 기반) |
| 매칭 중복 확정 | 동일 공고의 중복 매칭 생성 방지 | DB Unique 제약 (posting_id UNIQUE) |

### 7-2. 동시성 테스트 기준

```
100 Thread 동시 요청 시 재고 초과 0건
→ CountDownLatch 기반 동시성 테스트로 검증
→ Redisson 락 적용 전 실패 확인 → 적용 후 통과 확인 순서로 진행
```
