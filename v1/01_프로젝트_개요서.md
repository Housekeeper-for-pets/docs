## 2. 프로젝트 배경 및 목적

### 배경

국내 반려동물 양육 인구는 약 **1,500만 명**에 달하며 매년 증가하고 있다.
기존 펫시터·케어 서비스(케어네이처, 펫시팅닷컴 등)는 모두 **시터 주도** 구조로, 보호자가 수십 개의 시터 프로필을 일일이 탐색해야 하는 불편함이 있다.
ForPets는 보호자가 원하는 방식으로 시터를 구할 수 있도록 **순방향 검색과 역방향 매칭을 모두 지원**한다.

### 목적

- **양방향 매칭 구조 제공**: 보호자가 시터를 직접 검색·신청하는 순방향, 공고를 올리면 시터가 역으로 제안하는 역방향 모두 지원
- **실배포 경험**: 실제 사용 가능한 수준의 서비스를 AWS 환경에 배포하고 운영
- **AI 기능 통합 경험**: LLM 구조화 출력, Tool Calling, RAG, 장애 격리 등 AI Engineering 역량 습득 (확장)
- **동시성 제어 경험**: 매칭 확정 등 실제 트래픽 환경의 동시성 문제 직접 해결 (확장)

## 3. 서비스 개요

**ForPets(포펫츠)**는 반려동물 보호자와 펫시터를 연결하는 케어 매칭 플랫폼이다.
보호자는 **시터를 직접 검색해서 신청(순방향)** 하거나, **케어 조건을 공고로 올려 시터의 제안을 받는(역방향)** 두 가지 방식 중 원하는 방식을 선택할 수 있다.

### 핵심 가치 제안

| 가치 | 설명 |
|------|------|
| 순방향 매칭 | 보호자가 조건(지역·견종·예산 등)으로 시터를 직접 검색하고 케어를 신청 |
| 역방향 매칭 | 보호자가 케어 공고 등록 → 시터가 역으로 제안 입찰 → 보호자 선택. 기존 서비스에 없는 구조 |
| 실시간 케어 일지 | 시터가 케어 일지·사진을 등록하면 SSE로 보호자에게 실시간 푸시 |
| AI 시맨틱 탐색 | "분리불안 있는 노령견 경험 있는 시터" 등 자연어로 시터를 탐색하는 RAG 기반 검색 (확장) |

## 4. 핵심 비즈니스 로직

### 4-1. 순방향 매칭 플로우

> 보호자가 시터를 직접 탐색하고 케어를 신청하는 방식.

```
1. 보호자 → 조건(지역, 견종 크기, 예산 등)으로 시터 목록 검색 (QueryDSL 동적 필터)
2. 보호자 → 원하는 시터 프로필 확인 후 케어 신청
3. 시터   → 신청 수락 or 거절
4. 수락 시 → 매칭 확정 → 케어 진행
5. 시터   → 케어 일지·사진 등록 → SSE로 보호자 실시간 푸시
6. 보호자 → 케어 완료 확인 (Reservation 상태 → COMPLETED)
7. 보호자·시터 → 양방향 후기 작성 가능
```

### 4-2. 역방향 매칭 플로우

> 보호자가 조건을 공고로 올리면 시터가 역으로 제안하는 방식.

```
1. 보호자 → 케어 공고 등록 (날짜, 견종, 예산, 요구사항)
2. 시스템 → 조건 맞는 시터에게 SSE 알림 발송
3. 시터들 → 제안 입찰 (proposed_price, message)
4. 보호자 → 제안 목록 비교 후 최적 시터 1명 선택
5. 시스템 → 매칭 확정
   └ 중복 선택 불가 — DB Unique 제약 (posting_id UNIQUE)
6. 시터   → 케어 진행 + 일지/사진 업로드 → SSE로 보호자 실시간 푸시
7. 보호자 → 케어 완료 확인 (Reservation 상태 → COMPLETED)
8. 보호자·시터 → 양방향 후기 작성 가능
```

### 4-3. 매칭 상태 머신

```
[OPEN] ──제안 수락 / 신청 수락──▶ [MATCHED] ──케어 완료 확인──▶ [COMPLETED]
  │                                                                    │
만료/취소                                                        양방향 후기 작성
  │                                                                    ▼
  ▼                                                              [REVIEWED]
[CLOSED]
```

| 상태 | 설명 |
|------|------|
| `OPEN` | 공고 등록 완료 또는 케어 신청 대기. 제안·수락 가능 |
| `MATCHED` | 매칭 확정. 케어 진행 중 |
| `COMPLETED` | 보호자가 케어 완료 확인. 보호자·시터 양방향 후기 작성 가능 |
| `CLOSED` | 기간 만료 또는 보호자 취소 |

> **양방향 후기 기준:** Reservation 상태가 `COMPLETED`로 전환된 시점부터 보호자와 시터 모두 후기를 작성할 수 있다.

### 4-4. 동시성 제어 전략

> v1에서는 보호자가 최적 시터를 선택할 때 중복 확정이 발생하지 않도록 DB Unique 제약과 시터 제안 입찰 DB Unique 처리로 대응한다.
> Redisson 분산 락은 확장 기능에서 추가 도입을 검토한다.

| 시나리오 | 전략 | 시기 |
|----------|------|------|
| 매칭 중복 확정 방지 | DB Unique 제약 (posting_id UNIQUE) | v1 |
| 시터 제안 동시 입찰 | DB Unique 처리 | v1 |
| 분산 락 고도화 | Redisson 분산 락 (도전) | 확장 |

## 7. 기술 스택

### Backend

| 분류 | 기술 | 단계 | 선택 이유 |
|------|------|------|-----------|
| 언어/프레임워크 | Java 21 + Spring Boot 3.x | v1 필수 | Virtual Thread 지원, 팀 공통 학습 스택 |
| ORM | Spring Data JPA + QueryDSL | v1 필수 | 동적 검색 쿼리(시터·공고 필터), 타입 안전, N+1 해결 |
| 인증 | Spring Security + JWT | v1 필수 | Stateless 인증, 역할(보호자/시터/구조단체) 분리. 로그아웃은 Redis 블랙리스트로 처리 |
| 결제 | Portone | v1 필수 | 국내 표준 PG 연동, 웹훅 처리 간편 |
| 메시징 | Kafka | v1 필수 | 매칭 확정 → 결제·알림 비동기 파이프라인. 한 이벤트를 여러 소비자가 독립적으로 처리 |
| 실시간 | SSE | v1 필수 | 케어 일지·알림 단방향 푸시. WebSocket 대비 연결 비용 낮고 HTTP 기반이라 방화벽 이슈 없음 |
| 파일 저장 | AWS S3 | v1 필수 | 케어 일지 사진, 시터 프로필 이미지 저장·서빙 분리 |
| 분산 락 | Redisson | 확장 | 시터 제안 동시 입찰 정합성 고도화. v1에서는 DB Unique 제약으로 대응 |
| 실시간 채팅 | WebSocket STOMP | 확장 | 보호자-시터 1:1 채팅. 양방향 통신 필요 |
