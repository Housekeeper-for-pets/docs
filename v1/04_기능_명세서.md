## 문서 구조 안내

이 문서는 유스케이스 명세서(UC-001 ~ UC-016)를 **개발자가 바로 구현할 수 있는 기능 단위**로 세분화한다.
각 기능(FN)은 하나의 API 엔드포인트 또는 독립된 비즈니스 로직에 대응된다.

### 기능 ID 체계

```
FN-[도메인 약어]-[순번]

도메인 약어:
  AUTH    = 회원/인증
  PET     = 반려동물 관리
  POST    = 케어 공고
  PROP    = 시터 제안
  MATCH   = 매칭 확정
  LOG     = 케어 일지
  REVIEW  = 후기/평점
  RENTAL  = 용품 렌탈
  TEMP    = 임시보호
  NOTIFY  = 알림
  AI      = AI 기능
```

### 필수/도전 표기

| 표기 | 의미 |
|------|------|
| 🟢 필수 | Must Have — 2주차까지 반드시 완성 |
| 🔵 도전 | Should Have — 필수 완성 후 4~5주차에 진행 |

## 1. 회원·인증 도메인 (AUTH)

> **담당:** 권지원 / **연결 UC:** UC-001, UC-002, UC-003

---

### FN-AUTH-01: 회원가입 🟢

| 항목 | 내용 |
|------|------|
| 연결 UC | UC-001 |
| 담당 팀원 | 권지원 |
| API | `POST /api/auth/signup` |
| 인증 | 🔓 불필요 |

**기능 설명**

보호자·시터·구조단체가 이메일, 비밀번호, 닉네임, 역할을 입력하여 ForPets에 가입한다.

**입력값**

| 필드 | 타입 | 필수 | 검증 규칙 |
|------|------|:---:|-----------|
| email | String | ✅ | 이메일 형식, 최대 100자 |
| password | String | ✅ | 8자 이상, 영문+숫자 포함 |
| nickname | String | ✅ | 2~20자, 특수문자 불가 |
| role | Enum | ✅ | GUARDIAN, SITTER, RESCUE |

**처리 로직**

```
1. 입력값 유효성 검증 (Bean Validation)
2. 이메일 중복 조회
3. 비밀번호 BCrypt 암호화
4. User 엔티티 저장
5. 역할별 초기 프로필 생성:
   - SITTER → SitterProfile 빈 레코드 생성
   - RESCUE → RescueProfile 빈 레코드 생성
6. 성공 응답 반환
```

**응답**

| 상황 | HTTP 상태 | 응답 |
|------|-----------|------|
| 성공 | 201 Created | `{ "userId", "email", "role" }` |
| 이메일 중복 | 409 Conflict | "이미 가입된 이메일입니다." |
| 유효성 실패 | 400 Bad Request | 필드별 에러 메시지 |

**비고**

- 비밀번호 평문 로그 출력 금지
- 역할은 가입 시 1회만 선택 가능 (이후 변경 불가)

---

### FN-AUTH-02: 로그인 (JWT 발급) 🟢

| 항목 | 내용 |
|------|------|
| 연결 UC | UC-002 |
| 담당 팀원 | 권지원 |
| API | `POST /api/auth/login` |
| 인증 | 🔓 불필요 |

**기능 설명**

이메일/비밀번호 인증 후 JWT Access Token을 발급한다.

**입력값**

| 필드 | 타입 | 필수 |
|------|------|:---:|
| email | String | ✅ |
| password | String | ✅ |

**처리 로직**

```
1. 이메일로 사용자 조회
2. BCrypt 비밀번호 검증
3. JWT Access Token 생성
   - payload: { "userId", "role", "iat", "exp" }
   - 만료: 1시간
   - 서명: HS256 + 서버 Secret Key
4. 토큰 반환
```

**응답**

| 상황 | HTTP 상태 | 응답 |
|------|-----------|------|
| 성공 | 200 OK | `{ "accessToken": "eyJ..." }` |
| 인증 실패 | 401 Unauthorized | "이메일 또는 비밀번호가 올바르지 않습니다." |

**비고**

- 인증 실패 시 이메일 존재 여부를 구분하지 않음 (보안 원칙)
- Refresh Token은 이번 스코프에서 제외 (Out of Scope)

## 3. 케어 공고 도메인 (POST)

> **담당:** 박영수 / **연결 UC:** UC-005, UC-006

---

### FN-POST-01: 케어 공고 등록 🟢

| 항목 | 내용 |
|------|------|
| 연결 UC | UC-005 |
| 담당 팀원 | 박영수 |
| API | `POST /api/postings` |
| 인증 | 🔒 JWT 필수 (GUARDIAN) |

**기능 설명**

보호자가 케어 조건을 공고로 등록한다. 역방향 매칭의 출발점이다.

**입력값**

| 필드 | 타입 | 필수 | 검증 규칙 |
|------|------|:---:|-----------|
| petId | Long | ✅ | 본인 소유 반려동물 ID |
| title | String | ✅ | 1~100자 |
| description | String | ❌ | 최대 1,000자 (요구사항 상세) |
| startDate | LocalDate | ✅ | 오늘 이후 |
| endDate | LocalDate | ✅ | startDate 이후 |
| location | String | ✅ | 지역명 (시·구 단위) |
| budget | Integer | ✅ | 0 이상 (원 단위) |
| proposalDeadline | LocalDateTime | ✅ | startDate 이전 |

**처리 로직**

```
1. GUARDIAN 권한 확인
2. petId 존재 및 본인 소유 확인
3. startDate > 오늘 검증
4. proposalDeadline < startDate 검증
5. CarePosting 엔티티 저장 (status=OPEN, proposalCount=0)
6. SSE: 조건 매칭되는 시터들에게 실시간 알림 발송
7. 성공 응답 반환
```

**응답**

| 상황 | HTTP 상태 | 응답 |
|------|-----------|------|
| 성공 | 201 Created | `{ "postingId", "title", "status": "OPEN" }` |
| 과거 기간 | 400 Bad Request | "케어 기간은 오늘 이후여야 합니다." |
| 반려동물 없음 | 400 Bad Request | "반려동물을 먼저 등록해주세요." |

---

### FN-POST-02: 공고 목록 검색 (동적 필터) 🟢

| 항목 | 내용 |
|------|------|
| 연결 UC | UC-006 |
| 담당 팀원 | 박영수 |
| API | `GET /api/postings` |
| 인증 | 🔓 불필요 |

**기능 설명**

시터·보호자가 다양한 조건으로 케어 공고를 검색한다. QueryDSL 동적 쿼리로 구현한다.

**입력값 (Query Parameters)**

| 파라미터 | 타입 | 필수 | 기본값 |
|----------|------|:---:|--------|
| location | String | ❌ | 전체 |
| petSize | Enum | ❌ | 전체 (SMALL/MEDIUM/LARGE) |
| startDate | LocalDate | ❌ | — |
| endDate | LocalDate | ❌ | — |
| minBudget | Integer | ❌ | 0 |
| maxBudget | Integer | ❌ | 무제한 |
| status | Enum | ❌ | OPEN (기본 노출) |
| page | Integer | ❌ | 0 |
| size | Integer | ❌ | 20 |
| sort | String | ❌ | proposalDeadline,asc |

**처리 로직**

```
1. Redis 캐시 확인 (캐시 키: 조건 해시값)
   → 캐시 히트: 즉시 반환 (TTL 1분)
   → 캐시 미스: DB 조회 → 캐시 저장
2. QueryDSL 동적 WHERE 조건 생성
   (입력된 파라미터만 WHERE 절에 추가)
3. Page<CarePosting> 조회
4. DTO 변환 후 반환
   (공고 제목, 반려동물 정보, 예산, 제안 수, 마감일)
```

**응답**

```json
{
  "content": [
    {
      "postingId": 1,
      "title": "말티즈 3박 4일 케어 구해요",
      "petName": "뭉치",
      "petSize": "SMALL",
      "location": "서울 마포구",
      "budget": 60000,
      "proposalCount": 3,
      "proposalDeadline": "2026-06-30T23:59:59",
      "status": "OPEN"
    }
  ],
  "totalElements": 42,
  "totalPages": 3
}
```

**비고**

- 공고 상태가 CLOSED인 경우 기본 조회에서 제외
- 캐시 무효화: 신규 공고 등록·수정·마감 시 `@CacheEvict`

   - MEDICAL_CARE: "전문성·정확성" 강조 톤

| 필드 | 타입 | 필수 | 검증 규칙 |

| 타임아웃 | 대기 3초, 임대 10초 |
| 실패 전략 | Fail Fast (즉시 429 반환) |

### FN-MATCH-01: 제안 수락 (매칭 확정) 🟢

| 항목 | 내용 |
|------|------|
| 연결 UC | UC-008 |
| 담당 팀원 | 선경안 |
| API | `POST /api/postings/{postingId}/proposals/{proposalId}/accept` |
| 인증 | 🔒 JWT 필수 (GUARDIAN) |

**기능 설명**

보호자가 특정 시터의 제안을 수락하여 매칭을 확정한다. 중복 매칭은 DB Unique 제약으로 방지한다.

**처리 로직**

```
1. GUARDIAN 권한 확인 + 공고 작성자 본인 확인
2. proposalId로 SitterProposal 조회 (status=PENDING 확인)
3. DB 트랜잭션:
   a. Matching 엔티티 생성 (status=CONFIRMED)
      → posting_id UNIQUE 제약으로 중복 매칭 DB 레벨 차단
   b. CarePosting.status → MATCHED
   c. 수락 제안 외 나머지 SitterProposal → status=REJECTED
4. Kafka 매칭 확정 이벤트 발행 (topic: matching-confirmed)
   → Consumer 1: 결제 처리 (비동기)
   → Consumer 2: 시터에게 SSE 알림 "매칭이 확정되었습니다!"
   → Consumer 3: 케어 일정 생성
5. 보호자에게 매칭 확정 응답 반환
```

**Kafka 이벤트 설계**

```json
{
  "topic": "matching-confirmed",
  "payload": {
    "matchingId": 1,
    "postingId": 10,
    "guardianId": 5,
    "sitterId": 20,
    "finalPrice": 45000,
    "startDate": "2026-07-01",
    "endDate": "2026-07-04"
  }
}
```

**응답**

| 상황 | HTTP 상태 | 응답 |
|------|-----------|------|
| 성공 | 200 OK | `{ "matchingId", "status": "CONFIRMED", "finalPrice" }` |
| 이미 매칭된 공고 | 409 Conflict | "이미 매칭이 확정된 공고입니다." |
| 제안 없음 | 404 Not Found | "존재하지 않는 제안입니다." |

**비고**

- Kafka 이벤트 발행 실패 시 DLQ(Dead Letter Queue)에 적재 후 재처리
- 보호자 응답은 Kafka 소비 완료를 기다리지 않음 (비동기)

### FN-AI-01: AI 시터 추천 챗봇 (Tool Calling) 🔵

| 항목 | 내용 |
|------|------|
| 연결 UC | UC-016 |
| 담당 팀원 | 선경안 |
| API | `POST /api/ai/chat` |
| 인증 | 🔒 JWT 필수 |

**기능 설명**

자연어 질의에 LLM이 @Tool 메서드를 순차 호출하여 실시간 데이터를 포함한 응답을 SSE 스트리밍으로 반환한다.

**@Tool 메서드 목록**

| Tool | 설명 |
|------|------|
| `searchSitters(location, petSize, specialty)` | 조건 맞는 시터 목록 조회 |
| `getReviews(sitterId)` | 특정 시터의 후기 목록 조회 |
| `checkAvailability(sitterId, startDate, endDate)` | 시터 가용 일정 확인 |

**처리 로직**

```
1. JWT에서 userId 추출 + 세션 ID 확인
2. Redis에서 이전 대화 히스토리 조회 (최근 10턴 윈도우)
3. 히스토리 + 현재 질의를 LLM에 전송
4. LLM이 필요 시 @Tool 메서드 순차 호출
5. SSE 스트리밍으로 응답 전송 (글자 단위)
6. Redis에 대화 히스토리 저장 (세션 만료: 30분)
```

**Fallback 전략**

| 장애 유형 | 처리 방식 |
|----------|-----------|
| Tool 호출 실패 | 실패 컨텍스트를 LLM에 전달 → "조회에 실패했습니다. 직접 검색을 이용해주세요." |
| LLM 타임아웃 | Circuit Breaker 오픈 → "AI 서비스를 일시적으로 이용할 수 없습니다." |

## 13. 핵심 설계 원칙

- **서버 타임존**: KST(UTC+9) 기준 — 모든 datetime 필드 저장 및 반환 기준
- **역방향 매칭**: 보호자가 공고 등록 → 시터가 역으로 제안하는 구조. 기존 서비스 대비 핵심 차별화
- **동시성 제어**: Redisson 분산 락으로 시터 제안 동시 입찰 + 렌탈 재고 동시 차감 정합성 보장
- **비동기 처리**: Kafka로 매칭 확정 이벤트 → 결제·알림·일정 생성을 독립적으로 소비
- **실시간성**: SSE + Redis Pub/Sub으로 다중 서버 환경에서도 케어 일지·알림 실시간 전달
- **AI 장애 격리**: AI 장애 시에도 핵심 서비스(공고·매칭·렌탈)는 정상 동작. Circuit Breaker + Fallback 필수
