## 문서 구조 안내

이 문서는 유스케이스 명세서(UC)를 **개발자가 바로 구현할 수 있는 기능 단위**로 세분화한다.
각 기능(FN)은 하나의 API 엔드포인트 또는 독립된 비즈니스 로직에 대응된다.

### 기능 ID 체계

```
FN-[도메인 약어]-[순번]

도메인 약어:
  AUTH    = 회원/인증
  PET     = 반려동물 관리
  SITTER  = 시터 프로필
  POST    = 케어 공고
  REQ     = 순방향 케어 신청
  PROP    = 시터 제안 (역방향)
  MATCH   = 매칭 확정
  LOG     = 케어 일지
  REVIEW  = 후기/평점
  NOTIFY  = 알림
  PAY     = 결제
  AI      = AI 기능 (확장)
```

### 필수/확장 표기

| 표기 | 의미 |
|------|------|
| 🟢 필수 | v1 MVP — 반드시 완성 |
| 🔵 확장 | v1 완료 후 순차 추가 |

## 1. 회원·인증 도메인 (AUTH)

> **담당:** 팀원 1 / **연결 UC:** UC-001, UC-002, UC-002-1, UC-003

---

### FN-AUTH-01: 회원가입 🟢

| 항목 | 내용 |
|------|------|
| 연결 UC | UC-001 |
| 담당 팀원 | 팀원 1 |
| API | `POST /api/auth/signup` |
| 인증 | 🔓 불필요 |

**기능 설명**

보호자·시터·구조단체가 이메일, 비밀번호, 닉네임, 역할을 입력하여 ForPets에 가입한다.

**입력값**

| 필드 | 타입 | 필수 | 검증 규칙 |
|------|------|:---:|-----------|
| email | String | ✅ | 이메일 형식, 최대 100자 |
| password | String | ✅ | 8자 이상, 영문+숫자 포함 |
| nickname | String | ✅ | 2~20자, 특수문자 불가 |
| role | Enum | ✅ | GUARDIAN, SITTER, RESCUE |

**처리 로직**

```
1. 입력값 유효성 검증 (Bean Validation)
2. 이메일 중복 조회
3. 비밀번호 BCrypt 암호화
4. User 엔티티 저장
5. 역할별 초기 프로필 생성:
   - SITTER → SitterProfile 빈 레코드 생성
6. 성공 응답 반환
```

**응답**

| 상황 | HTTP 상태 | 응답 |
|------|-----------|------|
| 성공 | 201 Created | `{ "userId", "email", "role" }` |
| 이메일 중복 | 409 Conflict | "이미 가입된 이메일입니다." |
| 유효성 실패 | 400 Bad Request | 필드별 에러 메시지 |

---

### FN-AUTH-02: 로그인 (JWT 발급) 🟢

| 항목 | 내용 |
|------|------|
| 연결 UC | UC-002 |
| 담당 팀원 | 팀원 1 |
| API | `POST /api/auth/login` |
| 인증 | 🔓 불필요 |

**처리 로직**

```
1. 이메일로 사용자 조회
2. BCrypt 비밀번호 검증
3. JWT Access Token 생성
   - payload: { "userId", "role", "iat", "exp" }
   - 만료: 1시간
   - 서명: HS256 + 서버 Secret Key
4. 토큰 반환
```

**응답**

| 상황 | HTTP 상태 | 응답 |
|------|-----------|------|
| 성공 | 200 OK | `{ "accessToken": "eyJ..." }` |
| 인증 실패 | 401 Unauthorized | "이메일 또는 비밀번호가 올바르지 않습니다." |

---

### FN-AUTH-03: 로그아웃 (JWT 블랙리스트) 🟢

| 항목 | 내용 |
|------|------|
| 연결 UC | UC-002-1 |
| 담당 팀원 | 팀원 1 |
| API | `POST /api/auth/logout` |
| 인증 | 🔒 JWT 필수 |

**기능 설명**

현재 JWT Access Token을 Redis 블랙리스트에 등록하여 즉시 무효화한다.

**처리 로직**

```
1. JWT에서 userId 및 만료 시간(exp) 추출
2. 토큰을 Redis 블랙리스트에 SET
   - 키: "blacklist:{token}"
   - TTL: 토큰 잔여 만료 시간 (exp - now())
3. 이후 JwtAuthFilter에서 블랙리스트 조회 → 401 반환
4. 성공 응답 반환
```

**응답**

| 상황 | HTTP 상태 | 응답 |
|------|-----------|------|
| 성공 | 200 OK | "로그아웃되었습니다." |

**비고**

- 블랙리스트 키 TTL은 토큰 만료 시간과 동일하게 설정 → 만료 토큰 자동 삭제
- 클라이언트 측 토큰 삭제와 서버 측 블랙리스트 등록 병행

## 4. 케어 공고 도메인 (POST)

> **담당:** 팀원 2 / **연결 UC:** UC-006, UC-007

---

### FN-POST-01: 케어 공고 등록 (역방향) 🟢

| 항목 | 내용 |
|------|------|
| 연결 UC | UC-006 |
| 담당 팀원 | 팀원 2 |
| API | `POST /api/postings` |
| 인증 | 🔒 JWT 필수 (GUARDIAN) |

**기능 설명**

보호자가 케어 조건을 공고로 등록한다. 역방향 매칭의 출발점.

**입력값**

| 필드 | 타입 | 필수 | 검증 규칙 |
|------|------|:---:|-----------|
| petId | Long | ✅ | 본인 소유 반려동물 ID |
| title | String | ✅ | 1~100자 |
| description | String | ❌ | 최대 1,000자 |
| startDate | LocalDate | ✅ | 오늘 이후 |
| endDate | LocalDate | ✅ | startDate 이후 |
| location | String | ✅ | 지역명 (시·구 단위) |
| budget | Integer | ✅ | 0 이상 (원 단위) |
| proposalDeadline | LocalDateTime | ✅ | startDate 이전 |

**처리 로직**

```
1. GUARDIAN 권한 확인
2. petId 존재 및 본인 소유 확인
3. startDate > 오늘 검증
4. proposalDeadline < startDate 검증
5. CarePosting 엔티티 저장 (status=OPEN)
6. 💾 공고 목록 캐시 무효화 (@CacheEvict)
7. SSE: 조건 매칭되는 시터들에게 실시간 알림 발송
8. 성공 응답 반환
```

**응답**

| 상황 | HTTP 상태 | 응답 |
|------|-----------|------|
| 성공 | 201 Created | `{ "postingId", "title", "status": "OPEN" }` |
| 과거 기간 | 400 Bad Request | "케어 기간은 오늘 이후여야 합니다." |
| 반려동물 없음 | 400 Bad Request | "반려동물을 먼저 등록해주세요." |

### FN-AI-01: AI 시터 프로필 자동 생성 🔵

| 항목 | 내용 |

**기능 설명**

시터가 경력·전문 견종·특기를 입력하면 LLM이 카테고리에 맞는 프로필 문구를 **구조화된 JSON 포맷**으로 생성하고 DB에 저장한다.

**입력값**

| 필드 | 타입 | 필수 |
|------|------|:---:|
| specialty | Enum | ✅ | SMALL_DOG, SENIOR_DOG, MEDICAL_CARE |
| experienceYears | Integer | ✅ |
| breeds | List\<String\> | ✅ |
| skills | List\<String\> | ❌ |

**처리 로직**

```
1. specialty 기반 프롬프트 분기:
   - SMALL_DOG: 소형견 전문 톤 ("귀엽고 섬세한 케어" 강조)
   - SENIOR_DOG: 노령견 신뢰·안정감 톤 ("안전과 편안함" 강조)
   - MEDICAL_CARE: 전문성·정확성 톤 ("자격증·응급처치" 강조)
2. LLM API 호출 (Circuit Breaker 감시, 타임아웃 5초)
3. JSON 구조화 출력 파싱 (아래 스키마 필수 준수)
4. 파싱 실패 시 → Fallback 처리
5. SitterProfile.aiGeneratedBio 컬럼에 JSON 문자열로 저장
```

**LLM 응답 JSON 스키마 (구조화 출력 필수)**

```json
{
  "title": "String — 시터 프로필 제목 (최대 50자)",
  "description": "String — 소개글 본문 (100~300자)",
  "specialties": ["String", "..."],
  "keywords": ["String", "..."]
}
```

> **프롬프트 설계 원칙:**
> - 응답은 반드시 위 JSON 포맷만 반환. 마크다운·코드 블록·추가 텍스트 금지.
> - 출력 언어: 한국어
> - 스키마 외 필드 포함 시 파싱 오류로 간주 → Fallback 처리

**DB 컬럼 매핑**

| LLM 응답 필드 | DB 컬럼 | 타입 |
|--------------|---------|------|
| title | sitter_profile.ai_title | VARCHAR(100) |
| description | sitter_profile.ai_description | TEXT |
| specialties | sitter_profile.ai_specialties | JSON |
| keywords | sitter_profile.ai_keywords | JSON |
| (생성 시각) | sitter_profile.ai_generated_at | DATETIME |

> `aiGeneratedBio` 단일 JSON 컬럼 대신 필드별 분리 저장 → 추후 검색 인덱스 활용 가능

**Fallback 전략**

| 장애 유형 | 처리 |
|----------|------|
| 타임아웃 (5초 초과) | 캐시된 카테고리별 기본 템플릿 반환 (`aiGenerated: false` 응답) |
| Rate Limit (429) | Circuit Breaker OPEN → "AI 서비스를 일시적으로 이용할 수 없습니다. 직접 작성해주세요." |
| JSON 파싱 실패 (스키마 불일치) | 재시도 1회 → 실패 시 기본 템플릿 Fallback |

**응답**

| 상황 | HTTP 상태 | 응답 |
|------|-----------|------|
| AI 생성 성공 | 200 OK | `{ "title", "description", "specialties", "keywords", "aiGenerated": true }` |
| Fallback (기본 템플릿) | 200 OK | `{ "title": "...", ..., "aiGenerated": false }` |
| Circuit Breaker OPEN | 503 Service Unavailable | `{ "code": "AI_SERVICE_UNAVAILABLE", "message": "AI 서비스를 이용할 수 없습니다." }` |

**비고**

- 프롬프트 내용은 외부 파일(DB 또는 S3)로 관리 → 서버 재배포 없이 수정 가능
- 프롬프트 개선 이력 최소 3회 기록 (변경 동기 → 토큰 변화 → 품질 변화)
- AI 기능 장애 시 핵심 서비스(매칭·결제)는 정상 동작 보장 (완전 격리)
