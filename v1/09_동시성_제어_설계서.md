## 1. 문제 정의

### 1-1. 시터 제안 동시 입찰 — proposal_count Race Condition

```
T=0ms  시터 A: POST /api/postings/10/proposals  ──┐
T=1ms  시터 B: POST /api/postings/10/proposals  ──┤──▶ 동시 도달
T=2ms  시터 C: POST /api/postings/10/proposals  ──┘

기대:
  - proposal_count = 3 (정확히 3씩 증가)
  - SitterProposal 3건 생성

위험 (제어 없을 때):
  - 3명이 동시에 proposal_count = 0을 읽음
  - 모두 1로 업데이트 → proposal_count = 1 (Lost Update)
  - 중복 제안 방지 체크 타이밍에 따라 동일 시터가 2번 제안될 수 있음
```

### 1-2. 렌탈 재고 동시 차감 — stock Race Condition

```
T=0ms  보호자 A: POST /api/rentals (itemId=3, stock=1)  ──┐
T=1ms  보호자 B: POST /api/rentals (itemId=3, stock=1)  ──┘ 동시 도달

기대: A만 성공, B는 즉시 409 "재고가 없습니다."
위험: 두 명이 동시에 stock = 1 확인 후 모두 차감
결과(제어 없을 때): stock = -1 (재고 초과 대여)
```

### 1-3. 매칭 중복 확정 — MATCHING UNIQUE Race Condition

```
T=0ms  보호자 A가 제안 1번 수락: POST .../proposals/1/accept  ──┐
T=1ms  (보호자가 빠르게 두 번 클릭 or 네트워크 재시도)          ──┘ 동시 도달

기대: 1번만 매칭 생성
위험: 2건의 MATCHING 생성 → 같은 공고에 2개 매칭 발생
```

### 1-4. 왜 단순 체크로는 부족한가?

```
Thread A: SELECT stock FROM rental_item WHERE item_id = 3  → stock = 1 (읽기)
Thread B: SELECT stock FROM rental_item WHERE item_id = 3  → stock = 1 (읽기, A가 아직 UPDATE 전)
Thread A: UPDATE rental_item SET stock = 0 WHERE item_id = 3  (쓰기)
Thread B: UPDATE rental_item SET stock = 0 WHERE item_id = 3  (쓰기)
→ 두 명 모두 재고 차감 성공으로 인식 — Lost Update 문제
```

## 2. 동시성 제어 전략 비교

| 전략 | 메커니즘 | 장점 | 단점 | ForPets 적용 |
|------|----------|------|------|--------------|
| **낙관적 락** | `@Version` + 충돌 시 재시도 | 충돌 적을 때 성능 우수 | 재시도 로직 복잡, 충돌 많으면 성능 저하 | 미사용 (충돌 빈번한 도메인이라 부적합) |
| **비관적 락** | `SELECT ... FOR UPDATE` | 구현 단순, 정합성 확실 | 락 대기 지연, 단일 DB 의존 | 매칭 완료 확인 등 DB 트랜잭션 범위 내 처리 |
| **Redisson RLock** | Redis SetNX + TTL + Watchdog | AOP 구조, 분산 환경 지원, 편의성 | Redis 의존성 | 시터 제안 입찰 ✅, 렌탈 재고 차감 ✅ |
| **DB UNIQUE 제약** | MATCHING.posting_id UNIQUE | DB 레벨 최종 방어 | 에러 처리 필요 | 매칭 중복 확정 방지 ✅ 2차 방어선 |

**락 획득 순서 (데드락 방지):**
```
① 제안 입찰 락   (Redis: lock:proposal:{postingId})
② DB 트랜잭션    (MySQL: InnoDB)
```
```
① 렌탈 재고 락   (Redis: lock:rental:{itemId})
② DB 트랜잭션    (MySQL: InnoDB)
```
> 항상 Redis 락 → DB 트랜잭션 순서 고정. 해제는 역순(DB 커밋 → Redis 락 해제).

## 3. 시나리오 매트릭스

### 시나리오 A: 시터 제안 동시 입찰 — Redisson 분산락

| 단계 | 시터 A (Thread1) | 시터 B (Thread2) | Redis 상태 |
|------|----------------|----------------|-----------|
| T=0 | `tryLock("lock:proposal:10", wait=3s, lease=10s)` → 성공 | `tryLock(...)` 대기 중 (waitTime=3s) | lock 키 SET |
| T=1 | 중복 제안 체크: existsBySitterIdAndPostingId → false | 대기 중... | - |
| T=2 | SitterProposal 엔티티 저장, proposalCount INCR | 대기 중... | - |
| T=3 | DB COMMIT, `unlock()` | lock 획득 성공 | lock 키 DEL |
| T=4 | 201 OK 반환 | 중복 제안 체크: existsBySitterIdAndPostingId → false | - |
| T=5 | - | SitterProposal 엔티티 저장, proposalCount INCR | - |
| T=6 | - | DB COMMIT, `unlock()`, 201 OK 반환 | lock 키 DEL |

**결과**: proposal_count = 2 (정확히 순차 증가) ✅

**락 획득 실패 케이스 (waitTime 초과):**
```
T=0  시터 C: tryLock(wait=3s) 시도 → 3초 대기 후 실패
T=3  waitTime 초과 → 즉시 429 PROPOSAL_LOCK_FAILED 반환
```

**코드 예시:**
```java
// SitterProposalService.java — Redisson RLock 기반
public ProposalResponse submitProposal(Long postingId, Long sitterId, ProposalRequest request) {
    String lockKey = "lock:proposal:" + postingId;
    RLock lock = redissonClient.getLock(lockKey);

    boolean acquired = false;
    try {
        // waitTime=3s: 3초 대기. leaseTime=10s: 최대 보유 시간.
        acquired = lock.tryLock(3, 10, TimeUnit.SECONDS);
        if (!acquired) {
            throw new TooManyRequestsException("PROPOSAL_LOCK_FAILED",
                "현재 처리 중입니다. 잠시 후 다시 시도해주세요.");
        }

        // 1. 공고 OPEN 상태 확인
        CarePosting posting = postingRepository.findById(postingId)
            .orElseThrow(() -> new NotFoundException("POSTING_NOT_FOUND", "공고를 찾을 수 없습니다."));
        if (posting.getStatus() != PostingStatus.OPEN) {
            throw new BadRequestException("POSTING_CLOSED", "이미 마감된 공고입니다.");
        }

        // 2. 중복 제안 체크 (락 내부)
        if (proposalRepository.existsBySitterIdAndPostingId(sitterId, postingId)) {
            throw new ConflictException("PROPOSAL_DUPLICATED", "이미 이 공고에 제안하셨습니다.");
        }

        // 3. SitterProposal 저장
        SitterProposal proposal = SitterProposal.builder()
            .postingId(postingId)
            .sitterId(sitterId)
            .proposedPrice(request.getProposedPrice())
            .message(request.getMessage())
            .status(ProposalStatus.PENDING)
            .build();
        proposalRepository.save(proposal);

        // 4. proposalCount 증가 (Dirty Checking)
        posting.incrementProposalCount();

        return ProposalResponse.from(proposal);
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        throw new RuntimeException("락 획득 중 인터럽트 발생", e);
    } finally {
        if (acquired && lock.isHeldByCurrentThread()) {
            lock.unlock();
        }
    }
}
```

### 시나리오 B: Redisson AOP 패턴 (리팩토링 시)

```java
// @RedisLock 커스텀 어노테이션
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface RedisLock {
    String key();           // SpEL 표현식
    long waitTime() default 3;
    long leaseTime() default 10;
    TimeUnit timeUnit() default TimeUnit.SECONDS;
}

// RedisLockAspect.java
@Aspect
@Component
@RequiredArgsConstructor
public class RedisLockAspect {
    private final RedissonClient redissonClient;

    @Around("@annotation(redisLock)")
    public Object around(ProceedingJoinPoint pjp, RedisLock redisLock) throws Throwable {
        String lockKey = SpELParser.parse(redisLock.key(), pjp);
        RLock lock = redissonClient.getLock(lockKey);

        boolean acquired = false;
        try {
            acquired = lock.tryLock(redisLock.waitTime(), redisLock.leaseTime(), redisLock.timeUnit());
            if (!acquired) {
                throw new TooManyRequestsException("LOCK_FAILED", "현재 처리 중입니다.");
            }
            return pjp.proceed();
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new RuntimeException("락 획득 중 인터럽트 발생", e);
        } finally {
            if (acquired && lock.isHeldByCurrentThread()) lock.unlock();
        }
    }
}

// 어노테이션만 붙이면 락 자동 적용
@RedisLock(key = "'lock:proposal:' + #postingId", waitTime = 3, leaseTime = 10)
public ProposalResponse submitProposal(Long postingId, Long sitterId, ProposalRequest request) {
    // 락 로직이 AOP로 분리되어 비즈니스 로직만 남음
    ...
}

@RedisLock(key = "'lock:rental:' + #itemId", waitTime = 5, leaseTime = 15)
public RentalResponse requestRental(Long itemId, Long userId, RentalRequest request) {
    ...
}

### 시나리오 C: 렌탈 재고 동시 차감 — Redisson 분산락 (Retry)

| 단계 | 보호자 A (Thread1) | 보호자 B (Thread2) | DB stock |
|------|-------------------|-------------------|---------|
| T=0 | `tryLock("lock:rental:3", wait=5s, lease=15s)` → 성공 | `tryLock(...)` 대기 (waitTime=5s) | 1 |
| T=1 | stock = 1 확인 → stock 차감 | 대기 중... | 1 |
| T=2 | Rental 엔티티 생성, DB COMMIT | 대기 중... | 0 |
| T=3 | `unlock()`, 201 OK | lock 획득 성공 | 0 |
| T=4 | - | stock = 0 확인 → 즉시 409 "재고가 없습니다." | 0 |
| T=5 | - | `unlock()` | 0 |

**결과**: A만 렌탈 성공, B는 재고 없음으로 거절. stock = 0 정확히 유지 ✅

**코드 예시:**
```java
// RentalService.java
public RentalResponse requestRental(Long itemId, Long userId, RentalRequest request) {
    String lockKey = "lock:rental:" + itemId;
    RLock lock = redissonClient.getLock(lockKey);

    boolean acquired = false;
    try {
        // waitTime=5s (렌탈은 잠깐 기다려서라도 성공이 UX에 유리)
        acquired = lock.tryLock(5, 15, TimeUnit.SECONDS);
        if (!acquired) {
            throw new TooManyRequestsException("RENTAL_LOCK_FAILED",
                "현재 신청이 많습니다. 잠시 후 다시 시도해주세요.");
        }

        // 재고 확인 (락 내부)
        RentalItem item = rentalItemRepository.findById(itemId)
            .orElseThrow(() -> new NotFoundException("ITEM_NOT_FOUND", "용품을 찾을 수 없습니다."));
        if (item.getStock() <= 0) {
            throw new ConflictException("RENTAL_OUT_OF_STOCK", "재고가 없습니다.");
        }

        // 재고 차감 + Rental 생성
        item.decrementStock();  // Dirty Checking
        Rental rental = Rental.builder()
            .itemId(itemId)
            .userId(userId)
            .startDate(request.getStartDate())
            .endDate(request.getEndDate())
            .totalPrice(item.getDailyPrice() * request.getDays())
            .status(RentalStatus.ACTIVE)
            .build();
        rentalRepository.save(rental);

        return RentalResponse.from(rental);
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        throw new RuntimeException("락 획득 중 인터럽트 발생", e);
    } finally {
        if (acquired && lock.isHeldByCurrentThread()) {
            lock.unlock();
        }
    }
}
```

### 시나리오 D: 매칭 중복 확정 방지 — DB UNIQUE 제약

| 단계 | 요청 1 | 요청 2 | DB |
|------|--------|--------|-----|
| T=0 | MATCHING INSERT (posting_id=10) | MATCHING INSERT (posting_id=10) | posting_id=10 없음 |
| T=1 | INSERT 성공 → COMMIT | INSERT → **PK 중복 에러** | posting_id=10 존재 |
| T=2 | 200 OK 반환 | 즉시 ROLLBACK | posting_id=10 고정 |

```sql
-- MATCHING DDL — posting_id UNIQUE로 중복 매칭 DB 레벨 원천 차단
CREATE TABLE matching (
    matching_id BIGINT AUTO_INCREMENT PRIMARY KEY,
    posting_id  BIGINT UNIQUE NOT NULL,   -- 공고당 1건만 허용
    proposal_id BIGINT UNIQUE NOT NULL,
    guardian_id BIGINT NOT NULL,
    sitter_id   BIGINT NOT NULL,
    -- ...
    FOREIGN KEY (posting_id)  REFERENCES care_posting(posting_id),
    FOREIGN KEY (proposal_id) REFERENCES sitter_proposal(proposal_id)
);
```

> Redisson 분산락이 1차 방어선이라면, MATCHING.posting_id UNIQUE 제약이 2차 방어선이다.
> 락 구현 버그나 Redis 장애 상황에서도 중복 매칭을 막는다.

### 시나리오 E: leaseTime 만료 중 처리 지연

**상황**: Redisson leaseTime(10초) 내에 비즈니스 로직이 완료되지 않을 경우

| 단계 | Thread A | Thread B | Redis | DB |
|------|---------|---------|-------|----|
| T=0 | `tryLock(wait=3s, lease=10s)` 성공 | `tryLock` 대기 → 실패 | lock TTL=10s | - |
| T=10s | **leaseTime 만료** — lock 키 자동 삭제 | - | lock 키 없음 | 미완료 |
| T=10.1s | 비즈니스 로직 아직 진행 중 | 새 요청: `tryLock` 성공 가능 | - | - |
| T=10.2s | - | 중복 체크 → 이미 제안/렌탈 존재 확인 → 409 | - | - |
| T=11s | 정상 완료 | 이미 409 반환됨 | - | 완료 |

**결과**: leaseTime 만료됐어도 DB 레벨 중복 체크가 2차 방어선으로 동작 ✅

> **왜 Watchdog(자동 연장)을 사용하지 않는가?**
> ```
> lock() → Watchdog 활성화, 30초마다 자동 연장 (무한 대기 위험)
> tryLock() → leaseTime 고정, 자동 연장 없음 (본 프로젝트 선택)
>
> ∴ tryLock 사용 시 leaseTime은 실제 처리 시간보다 충분히 길어야 한다.
>   leaseTime 10s는 DB 트랜잭션 통상 100ms~500ms 기준 여유 20배.
> ```

## 4. 매칭 상태 전이와 락 적용 범위

```
[매칭 상태 전이와 동시성 제어 적용 범위]

OPEN ──────────────────────────▶ MATCHED ──────────────────▶ DONE
      ← Redisson 분산락 적용 →           ← DB 트랜잭션 →
      ← (MATCHING UNIQUE 2차 방어선) ──────────────────────────▶

동시성 제어 저장소별 역할:
  Redis lock:proposal:{postingId}: 제안 입찰 경쟁 구간 보호 (leaseTime 10s)
  Redis lock:rental:{itemId}:      렌탈 재고 차감 경쟁 구간 보호 (leaseTime 15s)
  MySQL MATCHING.posting_id UNIQUE: 매칭 중복 확정 DB 레벨 방어
  MySQL CARE_POSTING.proposal_count: 제안 수 정합성 (Redisson 락 내부에서 갱신)
  MySQL RENTAL_ITEM.stock:           재고 정합성 (Redisson 락 내부에서 갱신)

동시성 제어 필요 여부:
  제안 입찰 (proposal_count 증가) : N명 동시 입찰 가능 → Redisson 분산락 ✅ 필수
  제안 수락 (매칭 확정)           : 동일 공고 동시 수락 → UNIQUE 제약 ✅
  렌탈 재고 차감                  : N명 동시 신청 가능 → Redisson 분산락 ✅ 필수
  케어 완료 확인                  : 단일 경로 → DB 트랜잭션 ✅
```

## 5. 동시성 테스트 시나리오

### 5-1. 시터 제안 동시 입찰 테스트

```java
@SpringBootTest
class ProposalConcurrencyTest {

    @Test
    @DisplayName("동시에 100명이 동일 공고에 제안 입찰 시 proposal_count가 정확히 증가해야 한다")
    void concurrentProposalTest() throws InterruptedException {
        // given
        int threadCount = 100;
        Long postingId = 10L;
        ExecutorService executor = Executors.newFixedThreadPool(threadCount);
        CountDownLatch latch = new CountDownLatch(threadCount);
        AtomicInteger successCount = new AtomicInteger(0);
        AtomicInteger failCount = new AtomicInteger(0);

        // when
        for (int i = 0; i < threadCount; i++) {
            final long sitterId = i + 1L;
            executor.submit(() -> {
                try {
                    proposalService.submitProposal(postingId, sitterId,
                        new ProposalRequest(40000, "제안 메시지"));
                    successCount.incrementAndGet();
                } catch (Exception e) {
                    failCount.incrementAndGet();
                } finally {
                    latch.countDown();
                }
            });
        }
        latch.await(30, TimeUnit.SECONDS);

        // then
        CarePosting posting = postingRepository.findById(postingId).orElseThrow();
        long dbProposalCount = proposalRepository.countByPostingId(postingId);

        // proposal_count가 실제 DB 제안 수와 일치해야 함
        assertThat(posting.getProposalCount()).isEqualTo((int) dbProposalCount);
        assertThat(successCount.get()).isEqualTo((int) dbProposalCount);
        log.info("성공: {}, 실패: {}, DB proposal_count: {}", successCount, failCount, dbProposalCount);
    }
}
```

### 5-2. 렌탈 재고 동시 차감 테스트

```java
@Test
@DisplayName("동시에 100명이 재고 1개인 용품에 렌탈 신청 시 1명만 성공해야 한다")
void concurrentRentalTest() throws InterruptedException {
    // given
    int threadCount = 100;
    Long itemId = 3L;   // stock = 1인 용품

    CountDownLatch latch = new CountDownLatch(threadCount);
    AtomicInteger successCount = new AtomicInteger(0);

        final long userId = i + 1L;

            try {
                rentalService.requestRental(itemId, userId,
                    new RentalRequest(LocalDate.of(2026, 7, 1), LocalDate.of(2026, 7, 4)));

            } finally {

### 5-3. 매칭 중복 확정 테스트

```java
@Test
@DisplayName("동일 공고에 동시에 2번 제안 수락 시 1건만 매칭이 생성되어야 한다")
void concurrentMatchingTest() throws InterruptedException {
    // given
    int threadCount = 2;
    Long postingId = 10L;
    Long proposalId = 5L;
    ExecutorService executor = Executors.newFixedThreadPool(threadCount);
    CountDownLatch latch = new CountDownLatch(threadCount);
    AtomicInteger successCount = new AtomicInteger(0);

    // when
    for (int i = 0; i < threadCount; i++) {
        executor.submit(() -> {
            try {
                matchingService.acceptProposal(postingId, proposalId, 1L);
                successCount.incrementAndGet();
            } catch (Exception ignored) {
            } finally {
                latch.countDown();
            }
        });
    }
    latch.await(10, TimeUnit.SECONDS);

    // then
    assertThat(successCount.get()).isEqualTo(1);
    long matchingCount = matchingRepository.countByPostingId(postingId);
    assertThat(matchingCount).isEqualTo(1L); // DB UNIQUE 제약으로 1건만 존재
}
```

### 5-4. 구현 순서 (발제 요구사항)

```
[1단계] 동시성 테스트 코드 작성 (실패 확인)
  └ 위 테스트 코드 먼저 작성
  └ 이 시점에 테스트는 반드시 실패해야 정상 (Lost Update 확인)

        ↓

[2단계] Redisson 분산락 구현 (필수)
  └ RedissonClient Bean 등록 (RedissonConfig)
  └ lock:proposal:{postingId} 분산락 적용 (ProposalService)
  └ lock:rental:{itemId} 분산락 적용 (RentalService)
  └ MATCHING.posting_id UNIQUE 제약 확인 (DDL)
  └ 테스트 재실행 → 통과 확인

        ↓ 도전 구현

[3단계] @RedisLock AOP 리팩토링
  └ @RedisLock 커스텀 어노테이션 + RedisLockAspect 구현
  └ 비즈니스 로직에서 락 코드 분리
  └ 동일 테스트로 AOP 버전 검증
  └ Lettuce vs Redisson 선택 근거 README에 정리
```

## 6. 모니터링 포인트

| 항목 | 확인 방법 | 임계값 / 조치 |
|------|-----------|-------------|
| 제안 입찰 락 실패율 | 429 PROPOSAL_LOCK_FAILED 로그 비율 | 높으면 waitTime 증가 검토 |
| 렌탈 락 실패율 | 429 RENTAL_LOCK_FAILED 로그 비율 | 높으면 재고 확충 또는 waitTime 증가 |
| MATCHING UNIQUE 충돌 | DataIntegrityViolationException 로그 | 발생 = 분산락 버그 → 즉시 조사 |
| Redisson leaseTime 초과 | leaseTime 내 트랜잭션 완료 여부 | 초과 빈번 시 leaseTime 값 증가 |
| DB 락 대기 타임아웃 | LockTimeoutException 로그 | 빈번 시 `lock.timeout` 값 조정 |

### 설정값 기준표

| 설정 | 시나리오 | 현재값 | 이유 |
|------|----------|--------|------|
| 제안 입찰 waitTime | lock:proposal | 3초 | Fail Fast — 즉시 응답이 UX에 유리 |
| 제안 입찰 leaseTime | lock:proposal | 10초 | DB 트랜잭션 500ms 기준 여유 20배 |
| 렌탈 waitTime | lock:rental | 5초 | Retry — 잠깐 기다려서라도 성공이 유리 |
| 렌탈 leaseTime | lock:rental | 15초 | DB 트랜잭션 500ms 기준 여유 30배 |
| `javax.persistence.lock.timeout` | 비관적 락 | 3,000ms | UX 개선 (기본 50s → 3s로 단축) |
