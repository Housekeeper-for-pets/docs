## UC-001: 회원가입

- **액터**: 보호자 / 시터
- **사전조건**: ForPets에 가입되어 있지 않은 상태
- **주요 흐름**:
  1. 이메일, 비밀번호, 닉네임, **역할(GUARDIAN/SITTER)** 을 입력한다.
  2. 시스템이 이메일 중복 여부를 검증한다.
  3. 시스템이 비밀번호를 BCrypt로 암호화하여 저장한다.
  4. 역할에 따라 초기 프로필(시터 프로필 등)이 생성된다.
  5. 회원가입 완료 응답을 반환한다.
- **대체 흐름**:
  - 2a. 이메일이 이미 존재하는 경우 → "이미 가입된 이메일입니다." (409 Conflict)
- **예외 흐름**:
  - 1a. 이메일 형식이 올바르지 않은 경우 → 400 Bad Request
  - 1b. 비밀번호가 정책(8자 이상, 영문+숫자)에 부합하지 않는 경우 → 400 Bad Request
- **사후조건**: 사용자 정보가 DB에 저장되고 로그인 가능한 상태가 된다.

## UC-002: 로그인

- **액터**: 모든 사용자
- **사전조건**: 회원가입 완료 상태
- **주요 흐름**:
  1. 이메일과 비밀번호를 입력한다.
  2. 시스템이 BCrypt 비밀번호를 검증한다.
  3. 인증 성공 시 JWT Access Token을 발급한다. (payload: userId, role, exp)
  4. 토큰 반환 (만료: 1시간)
- **대체 흐름**:
  - 2a. 비밀번호 불일치 → "이메일 또는 비밀번호가 올바르지 않습니다." (401 Unauthorized)
- **사후조건**: JWT Access Token을 보유하고 인증이 필요한 API를 호출할 수 있다.

## UC-002-1: 로그아웃

- **액터**: 모든 사용자
- **사전조건**: 로그인 상태 (유효한 JWT 보유)
- **주요 흐름**:
  1. 로그아웃 요청 시 현재 JWT Access Token을 추출한다.
  2. 해당 토큰을 Redis 블랙리스트에 등록한다. (TTL = 토큰 잔여 만료 시간)
  3. 이후 동일 토큰으로 들어오는 요청은 JwtAuthFilter에서 차단한다.
- **사후조건**: 기존 토큰으로 더 이상 API 호출이 불가하다.

- **사전조건**: 로그인 상태 (유효한 JWT 보유)
- **주요 흐름**:

## UC-004: 반려동물 등록·관리

- **액터**: 보호자 (Guardian)
- **사전조건**: 보호자로 로그인한 상태
- **주요 흐름**:
  1. 반려동물 정보 입력: 이름, 종(DOG/CAT/ETC), 견종, 나이, 체중, 크기(SMALL/MEDIUM/LARGE), 중성화 여부, 특이사항.
  2. Pet 엔티티 저장 (user_id FK)
  3. 등록된 반려동물은 케어 공고 등록 시 선택 가능
- **사후조건**: 반려동물 정보가 DB에 저장되고 공고 등록에 연결 가능한 상태가 된다.

## UC-005: 시터 프로필 등록·조회 ⭐

> **페르소나 연결**: 순방향 보호자 — "조건으로 시터를 검색해서 직접 신청하고 싶다"

- **액터**: 시터 (Sitter), 보호자 (Guardian)
- **주요 흐름 (시터 — 프로필 등록·수정)**:
  1. 시터가 자기소개, 전문 견종, 경력, 서비스 지역을 입력한다.
  2. SitterProfile 엔티티를 저장한다.
- **주요 흐름 (보호자 — 시터 목록 검색)**:
  1. 검색 조건 입력: 지역, 견종 크기, 경력 연수
  2. QueryDSL 동적 쿼리로 조건에 맞는 시터 목록 조회
  3. Redis 캐싱 확인 (캐시 히트 시 DB 조회 생략, TTL 1시간)
  4. 시터 목록 반환 (닉네임, 평점, 후기 수, 전문 분야, 서비스 지역)
- **예외 흐름**:
  - Redis 연결 실패 → DB 직접 조회로 Graceful Degradation
- **사후조건**: 시터 목록이 반환된다. 동일 조건 재검색 시 캐시 히트.

## UC-006: 케어 공고 등록 (역방향) ⭐

> **페르소나 연결**: 역방향 보호자 — "내 조건에 맞는 시터가 역으로 제안해주길 원한다"

- **액터**: 보호자 (Guardian)
- **사전조건**: 보호자로 로그인 상태, 반려동물 1마리 이상 등록 완료
- **주요 흐름**:
  1. 케어 공고 정보를 입력한다: 반려동물 선택, 케어 기간(start/end), 지역, 예산, 요구사항, 제안 마감일
  2. CarePosting 엔티티를 생성한다. (status=OPEN)
  3. 시스템이 조건 매칭되는 시터들에게 SSE 알림을 발송한다.
  4. 공고 등록 완료 응답을 반환한다.
- **대체 흐름**:
  - 1a. 케어 기간이 과거인 경우 → "케어 기간은 현재 이후여야 합니다." (400 Bad Request)
  - 1b. 등록된 반려동물이 없는 경우 → "반려동물을 먼저 등록해주세요." (400 Bad Request)
- **사후조건**: 케어 공고가 OPEN 상태로 저장되고, 시터들이 제안 입찰을 시작할 수 있다.

## UC-007: 케어 공고 검색·조회

- **액터**: 시터 (Sitter), 보호자 (Guardian)
- **사전조건**: 로그인 상태, 등록된 공고 1개 이상 존재
- **주요 흐름**:
  1. 검색 조건 입력: 지역, 기간, 견종 크기, 예산 범위, 페이지

  4. 공고 목록 반환 (공고 제목, 반려동물 정보, 예산, 제안 수, 마감일)
- **예외 흐름**:
  - Redis 연결 실패 → DB 직접 조회로 Graceful Degradation
- **사후조건**: 조건에 맞는 공고 목록이 반환된다.

## UC-008: 순방향 케어 신청 ⭐

> **페르소나 연결**: 순방향 보호자 — "마음에 드는 시터에게 직접 케어를 신청하고 싶다"

- **액터**: 보호자 (Guardian)
- **사전조건**: 보호자로 로그인 상태, 시터 프로필 조회 완료
- **주요 흐름**:
  1. 시터 프로필 화면에서 "케어 신청" 클릭
  2. 케어 일정(날짜·내용)을 입력한다.
  3. CareRequest 엔티티를 생성한다. (status=PENDING)
  4. 시터에게 SSE 알림을 발송한다. ("새 케어 신청이 도착했습니다!")
- **사후조건**: 케어 신청이 PENDING 상태로 저장되고 시터가 확인할 수 있다.

## UC-009: 순방향 신청 수락·거절 ⭐

> **페르소나 연결**: 시터 — "내 조건에 맞는 신청만 수락하고 싶다"

- **액터**: 시터 (Sitter)
- **사전조건**: 시터로 로그인 상태, PENDING 상태의 CareRequest 존재
- **주요 흐름 (수락)**:
  1. 신청 목록 화면에서 케어 신청 선택 후 수락
  2. Matching 엔티티를 생성한다. (status=MATCHED)
  3. CareRequest.status → ACCEPTED
  4. Kafka 매칭 확정 이벤트 발행 → 결제·알림 비동기 처리
  5. 보호자에게 SSE 알림 ("케어 신청이 수락되었습니다!")
- **주요 흐름 (거절)**:
  1. 시터가 거절 선택 → CareRequest.status → REJECTED
  2. 보호자에게 SSE 알림 ("케어 신청이 거절되었습니다.")
- **사후조건**: 수락 시 Matching MATCHED 상태로 생성, 거절 시 보호자 알림 전송.

## UC-010: 시터 제안 입찰 (역방향) ⭐

> **페르소나 연결**: 시터 — "공고에 바로 제안을 넣고 싶다"

- **액터**: 시터 (Sitter)
- **사전조건**: 시터로 로그인 상태, 대상 공고가 OPEN 상태
- **주요 흐름**:
  1. 공고 상세 화면에서 "제안하기" 클릭
  2. 제안 금액(proposed_price)과 메시지를 입력한다.
  3. 시스템이 해당 시터의 중복 제안 여부를 DB Unique 제약으로 확인한다.
     (sitter_id + posting_id UNIQUE → 중복 시 즉시 409)
  4. SitterProposal 엔티티를 저장한다. (status=PENDING)
  5. 보호자에게 SSE 알림을 발송한다. ("새 제안이 도착했습니다!")
  6. 제안 등록 완료 응답을 반환한다.
- **대체 흐름**:
  - 3a. 해당 시터가 이미 제안한 경우 → "이미 제안을 등록했습니다." (409 Conflict)
  - 1a. 공고가 MATCHED/CLOSED 상태인 경우 → "이미 마감된 공고입니다." (400 Bad Request)
- **사후조건**: SitterProposal이 PENDING 상태로 저장되고, 보호자에게 알림이 발송된다.

## UC-011: 제안 수락 — 매칭 확정 (역방향) ⭐

> **페르소나 연결**: 역방향 보호자 — "마음에 드는 시터의 제안을 수락하고 싶다"

- **액터**: 보호자 (Guardian)
- **사전조건**: 보호자로 로그인 상태, 해당 공고에 제안이 1건 이상 존재
- **주요 흐름**:
  1. 제안 목록 화면에서 특정 시터의 제안을 선택하여 수락한다.
  2. 시스템이 해당 공고의 중복 매칭 여부를 DB Unique 제약(posting_id UNIQUE)으로 방지한다.
  3. Matching 엔티티를 생성한다. (status=MATCHED)
  4. CarePosting 상태를 MATCHED로 변경한다.
  5. 수락되지 않은 다른 제안들의 상태를 REJECTED로 변경한다.
  6. Kafka 매칭 확정 이벤트를 발행한다.
     → 결제 처리 + 시터에게 "매칭 확정" SSE 알림 + 케어 일정 생성
  7. 보호자에게 매칭 확정 응답을 반환한다.
- **대체 흐름**:
  - 2a. 이미 다른 제안이 수락된 경우 (동시 요청) → DB Unique 제약으로 409 Conflict
- **예외 흐름**:
  - 결제 실패 시 → 보호자에게 "결제에 실패했습니다. 재결제를 진행해주세요." 알림 발송 및 재결제 화면 유도
- **사후조건**: Matching이 MATCHED 상태로 생성되고, 양쪽 사용자에게 알림이 발송된다.

## UC-012: 케어 일지 등록 ⭐

> **페르소나 연결**: 시터 — "케어 중 일지를 올리면 보호자가 실시간으로 볼 수 있으면 좋겠다"

- **액터**: 시터 (Sitter)
- **사전조건**: 시터로 로그인 상태, MATCHED 상태의 Matching 존재
- **주요 흐름**:
  1. 케어 일지 내용(텍스트)과 사진을 입력한다.
  2. CareLog 엔티티를 DB에 저장한다.
  3. 시스템이 SSE로 보호자에게 실시간 푸시를 전송한다.
     (Redis Pub/Sub 경유 → 다중 서버 환경에서도 전달 보장)
  4. 보호자 앱에서 일지 내용과 사진을 실시간으로 확인한다.
- **예외 흐름**:
  - 3a. SSE 연결이 끊긴 경우 → 알림 로그 저장 (재연결 시 미읽음 목록 제공)
- **사후조건**: CareLog가 DB에 저장되고, 보호자에게 실시간으로 전달된다.

## UC-013: 케어 완료 확인 ⭐

> **Reservation 상태 → COMPLETED 기준으로 양방향 후기 작성이 가능해진다.**

- **액터**: 보호자 (Guardian)
- **사전조건**: MATCHED 상태의 Matching 존재
- **주요 흐름**:
  1. 보호자가 "케어 완료 확인" 클릭
  2. Reservation(Matching).status → COMPLETED
  3. 시터에게 SSE 알림 ("보호자가 케어 완료를 확인했습니다. 후기를 작성할 수 있어요.")
  4. 보호자·시터 모두 후기 작성 가능 상태로 전환
- **사후조건**: Reservation이 COMPLETED 상태가 되고, 양측 모두 후기 작성이 가능해진다.

## UC-014: 후기 작성 (양방향) ⭐

- **액터**: 보호자 (Guardian), 시터 (Sitter)
- **사전조건**: Reservation 상태가 COMPLETED인 경우
- **주요 흐름 (보호자)**:
  1. 별점(1~5)과 텍스트 후기를 입력한다.
  2. Review 엔티티를 DB에 저장한다. (reviewer=보호자, reviewee=시터)
  3. 시터의 평균 평점을 Redis ZSET으로 갱신한다. (ZINCRBY)
- **주요 흐름 (시터)**:
  1. 별점(1~5)과 텍스트 후기를 입력한다.
  2. Review 엔티티를 DB에 저장한다. (reviewer=시터, reviewee=보호자)
- **대체 흐름**:
  - Reservation이 COMPLETED 상태가 아닌 경우 → "케어 완료 확인 후 후기를 작성할 수 있습니다." (400 Bad Request)
  - 이미 후기를 작성한 경우 → "이미 후기를 작성했습니다." (409 Conflict)
- **사후조건**: 후기가 저장되고, 시터 평점 랭킹이 실시간 갱신된다.

## UC-015: Portone 결제

- **액터**: 보호자 (Guardian)
- **사전조건**: 매칭 확정(MATCHED) 상태. 보호자는 결제 수단(카드 등)을 보유 중.
- **주요 흐름**:
  1. 매칭 확정 직후 시스템이 보호자에게 결제 화면을 제공한다.
  2. 보호자가 결제 수단을 선택하고 결제를 진행한다.
  3. 결제가 성공하면 보호자에게 "결제 완료" 알림이 발송되고, 케어 일정이 확정된다.
  4. 보호자는 결제 내역(금액, 케어 기간, 시터 이름)을 확인할 수 있다.
- **대체 흐름**:
  - 3a. 결제가 실패한 경우 → 보호자에게 "결제에 실패했습니다." 알림을 발송하고, **재결제 버튼이 포함된 안내 화면으로 유도**한다.
  - 3b. 결제 수단이 유효하지 않은 경우 → "유효하지 않은 결제 수단입니다. 다른 수단을 선택해주세요."
- **예외 흐름**:
  - 결제 시스템(Portone) 장애 시 → "일시적인 오류가 발생했습니다. 잠시 후 다시 시도해주세요." 안내 후 재시도 유도.
- **사후조건**: 결제가 완료되고 보호자가 결제 내역을 확인할 수 있다. 케어 일정이 시터에게도 공유된다.
- **비고 (구현 참고)**: 결제 실패 시 내부적으로 재처리 큐에 적재되어 자동 재시도. 상세 구현은 04_기능_명세서 FN-PAY-01 참고.

## UC-EX-001: AI 시터 프로필 자동 생성

- **액터**: 시터 (Sitter)
- **사전조건**: 시터로 로그인 상태
- **주요 흐름**:
  1. 시터가 경력·전문 견종·특기를 입력한다.
  2. 시스템이 카테고리(소형견/노령견/의료케어)에 맞는 프롬프트를 선택한다.
  3. LLM에게 구조화 출력 요청을 전송한다.
  4. JSON 스키마로 파싱 후 DB에 저장한다.
     `{ "title", "description", "specialties", "keywords" }`
  5. 시터가 생성된 프로필 내용을 확인·수정 후 저장한다.
- **대체 흐름**:
  - 3a. LLM 타임아웃(5초 초과) → Fallback: 카테고리별 기본 템플릿 반환
  - 3b. Rate Limit(429) → Circuit Breaker 오픈, "잠시 후 다시 시도해주세요." 안내
- **사후조건**: AI 생성 프로필이 SitterProfile에 저장된다.

## UC-EX-002: AI 시터 추천 챗봇

- **액터**: 보호자 (Guardian)
- **사전조건**: 보호자로 로그인 상태
- **주요 흐름**:
  1. 자연어로 질의를 입력한다. ("관절 안 좋은 7살 진돗개 맡길 시터 마포구에서 찾아줘")
  2. LLM이 Tool Calling으로 백엔드 API를 순차 호출한다.
     - `searchSitters(location, petSize, specialty)`
     - `getReviews(sitterId)`
  3. RAG: 시터 후기 벡터를 시맨틱 탐색하여 컨텍스트 주입
  4. SSE로 응답을 스트리밍한다.
  5. 멀티턴: Redis에 세션 히스토리 저장, 최근 10턴 윈도우 유지
- **예외 흐름**:
  - 전체 AI 장애 → "AI 서비스를 이용할 수 없습니다. 직접 검색을 이용해주세요." (핵심 서비스는 정상 동작)
- **사후조건**: 사용자가 맥락에 맞는 시터 추천 결과를 수신한다.
