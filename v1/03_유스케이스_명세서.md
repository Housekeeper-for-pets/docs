## UC-001: 회원가입

- **액터**: 보호자 / 시터 / 구조단체
- **사전조건**: ForPets에 가입되어 있지 않은 상태
- **주요 흐름**:
  1. 이메일, 비밀번호, 닉네임, **역할(GUARDIAN/SITTER/RESCUE)** 을 입력한다.
  2. 시스템이 이메일 중복 여부를 검증한다.
  3. 시스템이 비밀번호를 BCrypt로 암호화하여 저장한다.
  4. 역할에 따라 초기 프로필(보호자 프로필 또는 시터 프로필)이 생성된다.
  5. 회원가입 완료 응답을 반환한다.
- **대체 흐름**:
  - 2a. 이메일이 이미 존재하는 경우 → "이미 가입된 이메일입니다." (409 Conflict)
- **예외 흐름**:
  - 1a. 이메일 형식이 올바르지 않은 경우 → 400 Bad Request
  - 1b. 비밀번호가 정책(8자 이상, 영문+숫자)에 부합하지 않는 경우 → 400 Bad Request
- **사후조건**: 사용자 정보가 DB에 저장되고 로그인 가능한 상태가 된다.
- **관련 기능**: 필수 — 회원 관리, JWT 인증

## UC-002: 로그인

- **액터**: 모든 사용자
- **사전조건**: 회원가입 완료 상태
- **주요 흐름**:
  1. 이메일과 비밀번호를 입력한다.
  2. 시스템이 BCrypt 비밀번호를 검증한다.
  3. 인증 성공 시 JWT Access Token을 발급한다. (payload: userId, role, exp)
  4. 토큰 반환 (만료: 1시간)
- **대체 흐름**:
  - 2a. 비밀번호 불일치 → "이메일 또는 비밀번호가 올바르지 않습니다." (401 Unauthorized)
- **사후조건**: JWT Access Token을 보유하고 인증이 필요한 API를 호출할 수 있다.
- **관련 기능**: 필수 — JWT 인증

## UC-004: 반려동물 등록·관리

- **액터**: 보호자 (Guardian)
- **사전조건**: 보호자로 로그인한 상태
- **주요 흐름**:
  1. 반려동물 정보 입력: 이름, 종(DOG/CAT/ETC), 견종, 나이, 체중, 크기(SMALL/MEDIUM/LARGE), 중성화 여부, 특이사항.
  2. Pet 엔티티 저장 (user_id FK)

- **사후조건**: 반려동물 정보가 DB에 저장되고 공고 등록에 연결 가능한 상태가 된다.

## UC-005: 케어 공고 등록 ⭐

> **페르소나 연결**: 김보호 — "내 조건에 맞는 시터가 역으로 제안해주길 원한다"

- **액터**: 보호자 (Guardian)
- **사전조건**: 보호자로 로그인 상태, 반려동물 1마리 이상 등록 완료
- **주요 흐름**:
  1. 케어 공고 정보를 입력한다: 반려동물 선택, 케어 기간(start/end), 지역, 예산, 요구사항, 제안 마감일
  2. CarePosting 엔티티를 생성한다. (status=OPEN)
  3. 시스템이 조건 매칭되는 시터들에게 SSE 알림을 발송한다.
  4. 공고 등록 완료 응답을 반환한다.
- **대체 흐름**:
  - 1a. 케어 기간이 과거인 경우 → "케어 기간은 현재 이후여야 합니다." (400 Bad Request)
- **예외 흐름**:
  - 1b. 등록된 반려동물이 없는 경우 → "반려동물을 먼저 등록해주세요." (400 Bad Request)
- **사후조건**: 케어 공고가 OPEN 상태로 저장되고, 시터들이 제안 입찰을 시작할 수 있다.
- **관련 기능**: 필수 — 케어 공고 등록, SSE 알림

## UC-006: 케어 공고 검색·조회 ⭐

> **페르소나 연결**: 이탐색 — "내 조건에 맞는 공고를 빠르게 탐색하고 싶다"

- **액터**: 시터 (Sitter), 보호자 (Guardian)
- **사전조건**: 로그인 상태, 등록된 공고 1개 이상 존재
- **주요 흐름**:
  1. 검색 조건 입력: 지역, 기간, 견종 크기, 예산 범위, 페이지
  2. QueryDSL 동적 쿼리로 조건에 맞는 공고 목록 조회
  3. Redis 캐싱 확인 (캐시 히트 시 DB 조회 생략)
  4. 공고 목록 반환 (공고 제목, 반려동물 정보, 예산, 제안 수, 마감일)
- **대체 흐름**:
  - 4a. 검색 결과가 0건인 경우 → "검색 결과가 없습니다." 안내
- **예외 흐름**:
  - 3a. Redis 연결 실패 → DB 직접 조회로 Graceful Degradation
- **사후조건**: 조건에 맞는 공고 목록이 반환된다. 동일 조건 재검색 시 캐시 히트.
- **관련 기능**: 필수 — QueryDSL 동적 검색, Redis 캐싱

## UC-007: 시터 제안 입찰 ⭐

> **페르소나 연결**: 박시터 — "공고에 바로 제안을 넣고 싶다"

- **액터**: 시터 (Sitter)
- **사전조건**: 시터로 로그인 상태, 대상 공고가 OPEN 상태
- **주요 흐름**:
  1. 공고 상세 화면에서 "제안하기" 클릭
  2. 제안 금액(proposed_price)과 메시지를 입력한다.
  3. 시스템이 Redisson 분산 락을 획득한다. (`lock:proposal:{postingId}`)
  4. 락 내부에서 해당 시터의 중복 제안 여부를 확인한다.
  5. SitterProposal 엔티티를 저장한다. (status=PENDING)
  6. `proposal_count` 카운터를 증가시킨다.
  7. 분산 락을 해제한다.
  8. 보호자에게 SSE 알림을 발송한다. ("새 제안이 도착했습니다!")
  9. 제안 등록 완료 응답을 반환한다.
- **대체 흐름**:
  - 4a. 해당 시터가 이미 제안한 경우 → "이미 제안을 등록했습니다." (409 Conflict)
  - 1a. 공고가 MATCHED/CLOSED 상태인 경우 → "이미 마감된 공고입니다." (400 Bad Request)
- **예외 흐름**:
  - 3a. 분산 락 획득 실패 → Fail Fast "현재 처리 중입니다. 잠시 후 다시 시도해주세요." (429)
- **사후조건**: SitterProposal이 PENDING 상태로 저장되고, proposal_count가 정확히 증가한다.
- **관련 기능**: 필수 — 시터 제안 입찰, Redisson 분산 락, SSE 알림

## UC-008: 제안 수락 (매칭 확정) ⭐

> **페르소나 연결**: 김보호 — "마음에 드는 시터의 제안을 수락하고 싶다"

- **액터**: 보호자 (Guardian)
- **사전조건**: 보호자로 로그인 상태, 해당 공고에 제안이 1건 이상 존재
- **주요 흐름**:
  1. 제안 목록 화면에서 특정 시터의 제안을 선택하여 수락한다.
  2. 시스템이 해당 공고의 중복 매칭 여부를 DB Unique 제약으로 방지한다.
  3. Matching 엔티티를 생성한다. (status=CONFIRMED)
  4. CarePosting 상태를 MATCHED로 변경한다.
  5. 수락되지 않은 다른 제안들의 상태를 REJECTED로 변경한다.
  6. Kafka 매칭 확정 이벤트를 발행한다.
     → 소비자 1: 결제 처리
     → 소비자 2: 박시터에게 "매칭 확정" SSE 알림
     → 소비자 3: 케어 일정 생성
  7. 보호자에게 매칭 확정 응답을 반환한다.
- **대체 흐름**:
  - 2a. 이미 다른 제안이 수락된 경우 (동시 요청) → DB Unique 제약으로 409 Conflict
- **예외 흐름**:
  - 6a. Kafka 이벤트 발행 실패 → DLQ에 적재, 재처리 예약
- **사후조건**: Matching이 CONFIRMED 상태로 생성되고, 양쪽 사용자에게 알림이 발송된다.
- **관련 기능**: 필수 — 매칭 확정, Kafka 비동기 이벤트, SSE 알림

## UC-009: 케어 일지 등록 ⭐

> **페르소나 연결**: 박시터 — "케어 중 일지를 올리면 보호자가 실시간으로 볼 수 있으면 좋겠다"

- **액터**: 시터 (Sitter)
- **사전조건**: 시터로 로그인 상태, CONFIRMED 상태의 Matching 존재
- **주요 흐름**:
  1. 케어 일지 내용(텍스트)과 사진을 입력한다.
  2. CareLog 엔티티를 DB에 저장한다.
  3. 시스템이 SSE로 보호자에게 실시간 푸시를 전송한다.
     (Redis Pub/Sub 경유 → 다중 서버 환경에서도 전달 보장)
  4. 보호자 앱에서 일지 내용과 사진을 실시간으로 확인한다.
- **예외 흐름**:
  - 3a. SSE 연결이 끊긴 경우 → 알림 로그 저장 (재연결 시 미읽음 목록 제공)
- **사후조건**: CareLog가 DB에 저장되고, 보호자에게 실시간으로 전달된다.
- **관련 기능**: 필수 — SSE 실시간 전송, Redis Pub/Sub

## UC-010: 매칭 완료 후 후기 작성

- **액터**: 보호자 (Guardian)
- **사전조건**: 보호자가 케어 완료 확인을 누른 상태 (Matching status=DONE)
- **주요 흐름**:
  1. 별점(1~5)과 텍스트 후기를 입력한다.
  2. Review 엔티티를 DB에 저장한다.
  3. 시터의 평균 평점을 Redis ZSET으로 갱신한다. (ZINCRBY)
  4. AI 후기 요약 자동 생성 (비동기): 후기 텍스트 → LLM 구조화 출력 → ai_summary 필드 저장
- **사후조건**: 후기가 저장되고, 시터 평점 랭킹이 실시간 갱신된다.
- **관련 기능**: 필수 — 후기·평점, Redis ZSET / 도전 — AI 후기 요약

## UC-011: 용품 렌탈 신청 ⭐

> **페르소나 연결**: 김보호 — "켄넬을 단기 렌탈하고 싶다"

- **액터**: 보호자 (Guardian)
- **사전조건**: 보호자로 로그인 상태, 렌탈 가능한 용품 존재
- **주요 흐름**:
  1. 용품 검색 (카테고리, 지역, 기간, 가격)
  2. 렌탈 신청 (itemId, startDate, endDate)
  3. 시스템이 Redisson 분산 락을 획득한다. (`lock:rental:{itemId}`)
  4. 락 내부에서 재고(stock) 확인 → stock > 0이면 차감
  5. Rental 엔티티를 생성한다. (status=ACTIVE)
  6. 분산 락 해제
  7. 렌탈 확정 응답 반환
- **대체 흐름**:
  - 4a. 재고가 0인 경우 → 즉시 "재고가 없습니다." (409 Conflict)
- **예외 흐름**:
  - 3a. 분산 락 획득 실패 → Retry with backoff 최대 3회 → 실패 시 409
- **사후조건**: Rental이 ACTIVE 상태로 생성되고 재고가 정확히 차감된다.
- **관련 기능**: 필수 — 렌탈 신청, Redisson 분산 락

## UC-012: 렌탈 반납 처리

- **액터**: 보호자 (Guardian), 스케줄러
- **사전조건**: ACTIVE 상태의 Rental 존재
- **주요 흐름**:
  1. 보호자가 "반납 완료" 클릭 → Rental.returnDate 저장, status=RETURNED
  2. 재고(stock) 1 증가
- **대체 흐름 (자동)**:
  - 스케줄러가 매일 00:00에 endDate를 초과한 ACTIVE 렌탈 목록 조회
  - status=OVERDUE로 변경 + 하루당 50% 추가 패널티 자동 부과
- **사후조건**: 반납 완료 처리 또는 지연 패널티가 자동 부과된다.
- **관련 기능**: 필수 — 스케줄러 배치, 반납 지연 자동 패널티

## UC-015: AI 시터 프로필 자동 생성 ⭐

> **페르소나 연결**: 박시터 — "프로필 문구를 잘 못 쓰겠어서 AI 도움을 받고 싶다"

- **액터**: 시터 (Sitter)
- **사전조건**: 시터로 로그인 상태
- **주요 흐름**:
  1. 시터가 경력·전문 견종·특기를 입력한다.
  2. 시스템이 카테고리(소형견/노령견/의료케어)에 맞는 프롬프트를 선택한다.
  3. LLM에게 구조화 출력 요청을 전송한다.
  4. JSON 스키마로 파싱 후 DB에 저장한다.
     `{ "title", "description", "specialties", "keywords" }`
  5. 시터가 생성된 프로필 내용을 확인·수정 후 저장한다.
- **대체 흐름**:
  - 3a. LLM 타임아웃(5초 초과) → Fallback: 캐시된 기본 템플릿 반환
  - 3b. Rate Limit(429) → Circuit Breaker 오픈, "잠시 후 다시 시도해주세요." 안내
- **사후조건**: AI 생성 프로필이 SitterProfile.ai_generated_bio 필드에 저장된다.
- **관련 기능**: 도전 — LLM 구조화 출력 (AI 필수 1), AI 장애 격리 (AI 필수 3)

## UC-016: AI 시터 추천 챗봇 ⭐

> **페르소나 연결**: 이탐색 — "자연어로 물어보면 딱 맞는 시터를 찾아주길 원한다"

- **액터**: 보호자 (Guardian)
- **사전조건**: 보호자로 로그인 상태
- **주요 흐름**:
  1. 자연어로 질의를 입력한다. ("관절 안 좋은 7살 진돗개 맡길 시터 마포구에서 찾아줘")
  2. LLM이 Tool Calling으로 백엔드 API를 순차 호출한다.
     - `searchSitters(location, petSize, specialty)`
     - `getReviews(sitterId)`
  3. RAG: 시터 후기 벡터를 시맨틱 탐색하여 컨텍스트 주입
  4. SSE로 응답을 스트리밍한다.
  5. 멀티턴: Redis에 세션 히스토리 저장, 최근 10턴 윈도우 유지
- **대체 흐름**:
  - 2a. Tool 호출 실패 → LLM이 "조회에 실패했습니다. 직접 검색을 이용해주세요." 자연어 안내
  - 3a. RAG 유사도 임계값(0.7) 미만 → 해당 결과 컨텍스트 제외, Fallback 응답
- **예외 흐름**:
  - 전체 AI 장애 → "AI 서비스를 이용할 수 없습니다. 직접 검색을 이용해주세요." (핵심 서비스는 정상 동작)
- **사후조건**: 사용자가 맥락에 맞는 시터 추천 결과를 수신한다. 세션 히스토리가 Redis에 저장된다.
- **관련 기능**: 도전 — Tool Calling (AI 필수 2), RAG (AI 도전 1), SSE 스트리밍 + 멀티턴 (AI 도전 2)
